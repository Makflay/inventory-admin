# Inventory Admin

Inventory Admin — fullstack-приложение для работы с большим логическим набором идентификаторов. Проект демонстрирует серверную пагинацию и поиск, эффективный рендеринг длинных списков, пакетную обработку запросов и согласование оптимистичных изменений с состоянием сервера.

## 1. О проекте и демо

Приложение работает с базовым диапазоном ID `1...1_000_000` и дополнительными пользовательскими ID. Интерфейс разделён на две колонки: доступные и выбранные элементы.

Пользователь может искать ID, выбирать и отменять выбор, добавлять собственные ID и менять порядок выбранных элементов.

- **Demo:** [https://inventory-admin-client.onrender.com](https://inventory-admin-client.onrender.com)
- **API health:** [https://inventory-admin-lhue.onrender.com/api/health](https://inventory-admin-lhue.onrender.com/api/health)

Backend размещён на бесплатном тарифе Render, поэтому после периода бездействия первый запрос может потребовать время на cold start (холодный запуск).

## 2. Возможности и технологии

Основные возможности:

- независимый поиск по ID в обеих колонках;
- выбор и отмена выбора элементов;
- добавление custom ID (пользовательского ID);
- двунаправленная infinite scroll (бесконечная прокрутка);
- изменение порядка выбранных элементов;
- filtered DnD (перетаскивание с учётом активного фильтра).

**Frontend:** React, TypeScript, Vite, MUI, TanStack Virtual, dnd-kit.

**Backend:** Node.js, Express, TypeScript.

**Общая инфраструктура:** npm workspaces, общие TypeScript-контракты между frontend и backend, развертывание на Render.

## 3. Локальный запуск

Требуются Node.js и npm. Все команды выполняются из корня проекта в Bash.

Установите зависимости:

```bash
npm ci
```

Создайте локальные файлы переменных окружения:

```bash
cp client/.env.example client/.env
cp server/.env.example server/.env
```

Соберите общий workspace с контрактами:

```bash
npm run build:shared
```

Запустите backend:

```bash
npm run dev:server
```

В отдельной Bash-консоли запустите frontend:

```bash
npm run dev:client
```

После запуска доступны:

- Frontend: [http://localhost:5173](http://localhost:5173)
- Backend: [http://localhost:3000](http://localhost:3000)
- Health: [http://localhost:3000/api/health](http://localhost:3000/api/health)

`VITE_API_URL` - Публичный адрес backend, используемый frontend
`PORT` - Порт на котором запускается backend
`CLIENT_ORIGIN` - Разрешённый CORS origin frontend

## 4. Архитектура и ключевые решения

### 1. Миллион ID без материализации

Базовый диапазон `1...1_000_000` не хранится на backend как массив из миллиона элементов. Существование ID и содержимое страниц вычисляются логически. Отдельно хранятся только пользовательские ID, множество выбранных элементов и их порядок.

### 2. Cursor pagination (курсорная пагинация) и поиск

Backend возвращает страницы максимум по 20 ID. Для загрузки следующей и предыдущей страницы используются границы `after` и `before`, поэтому список можно загружать в обе стороны.

Поиск выполняется на backend по десятичному представлению ID и продолжает пагинацию внутри отфильтрованной выборки. Клиенту не требуется получать полный список.

### 3. Virtualization (виртуализация) и bounded cache (ограниченный кеш)

TanStack Virtual ограничивает количество одновременно созданных DOM-элементов видимой областью и небольшим запасом.

Frontend хранит ограниченный кеш примерно до 250 страниц, или 5000 ID, вместо бесконечного накопления загруженных данных. Старые страницы вытесняются, а отсутствующие области при возврате пользователя могут быть загружены повторно от ближайшей сохранённой границы.

### 4. Batching (пакетная обработка) и согласованность состояния

Одинаковые read-запросы (запросы чтения) дедуплицируются и объединяются в пакеты. Изменения выбора, порядка и добавление ID также отправляются пакетами.

Интерфейс использует optimistic UI (оптимистичное обновление интерфейса), поэтому действие отображается сразу. После ответа выполняется сверка с authoritative state (авторитетным состоянием сервера). Монотонный `serverVersion` помогает обнаруживать и отбрасывать stale responses (устаревшие ответы).

### 5. Порядок выбранных элементов и filtered DnD

`selectedIds` отвечает за принадлежность ID к выбранным, а `selectedOrder` хранит порядок отображения.

Drag-and-drop / DnD (перетаскивание элементов) работает и при активном поиске. Перемещаются только видимые подходящие элементы, а позиции скрытых фильтром ID сохраняются.

## 5. Развертывание

Frontend развернут как **Render Static Site**, backend — как **Render Web Service**.

Frontend-сборка требует `VITE_API_URL`. Backend во время запуска требует `CLIENT_ORIGIN`, а `PORT` предоставляется hosting platform (платформой размещения).

Workspace `shared` должен быть собран раньше `client` и `server`, поскольку содержит общие контракты.

- Frontend artifact (результат production-сборки): `client/dist`
- Backend entrypoint (точка запуска): `server/dist/index.js`

## 6. Ограничения

Backend использует in-memory storage (хранение состояния в памяти процесса).

Поэтому:

- обновление страницы браузера не очищает состояние backend;
- перезапуск backend сбрасывает пользовательские ID, выбранные элементы и `serverVersion`;
- после перезапуска backend открытый frontend рекомендуется обновить;
- бесплатный Render может переходить в режим сна и иметь cold start;
- приложение не предназначено для долговременного хранения данных.
